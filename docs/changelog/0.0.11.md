# Pi Agent Chat 0.0.11

## Added

- **Retry a request that failed for good**: whenever a turn ends on a request that never came back — a
  connection error automatic retry gave up on, a timeout with retry switched off, or an error that was
  never retriable — the transcript now closes with a **Retry** button that re-issues the same request.
  Carrying on no longer costs a "continue" message that ends up in the transcript and in the model
  context saying nothing about the task.

- **The offer survives a window reload**: the retry notice is a transcript event, so a window that
  reopens the session later would replay nothing but the bare provider error (`Request timed out.`).
  The offer is therefore recomputed from the session state at replay time — the failed response is
  still the last message, so the retry remains meaningful — and it is attached to the copy sent to the
  webview only, never accumulated into the stored history.

## Design notes

- Re-issuing works the way the SDK's own automatic retry does between two attempts: drop the failed
  response from agent state (the session file keeps it, exactly as the SDK leaves it), then continue
  through the session's own prompt path with an empty message batch. No new message is appended, so
  the conversation reads as if the connection had held.

- The offer is made when everything automatic has settled (`agent_settled`), not when a "retry failed"
  notice appears: one rule covers all three ways a turn can die, and one failure produces exactly one
  button, always at the end of the transcript.

- Whether a retry is still possible is decided by the host from the session state, never by the button
  (a click can always be stale, since the notice stays in the transcript). Only a turn that stopped on
  `stopReason === "error"` qualifies: re-running a turn that ended normally would silently discard the
  answer on screen. Subagent lanes never get the button — a lane's failed turn is reported to the
  parent agent, whose job it is to decide what to do.

- The SDK entry point the resume rides on is private, so its presence is feature-detected; if a future
  SDK renames it, the action degrades to "no button" rather than a button that quietly fails.

## Internal

- New `agent/resume.ts` module (resumability check + resume mechanics) wired into `ChatBridge` via
  `offerRetry()` / `withRetryOffer()` / the `retry` webview message; the webview draws the action on a
  new actionable notice card that stays out of the (collapsed) work block so the button is reachable.
- Two new offline self-checks in `diagnostics.ts`: `manual retry` pins the private SDK prompt path and
  that resuming re-issues the request without inventing a user message; `replayed retry offer` follows
  a session file that ends on a failed response through `PiRuntime` and a real `ChatBridge.attach()`
  down to the `history` message actually posted.
