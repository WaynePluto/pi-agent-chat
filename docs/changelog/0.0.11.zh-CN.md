# Pi Agent Chat 0.0.11

## 新增

- **失败请求的手动重发**：只要一轮对话停在没有回来的请求上——自动重试放弃的连接错误、关闭自动重试后的超时、压根不可重试的错误——transcript 末尾就会给出一个**重试**按钮，直接重发同一次请求。不必再打一句「继续」，也就不会在对话和模型上下文里多出一条与任务无关的消息。

- **该提议在窗口重载后依然存在**：重试通知是 transcript 事件，重开会话的窗口只会回放出一条赤裸的 provider 错误（`Request timed out.`）。因此回放时会按会话状态重新计算该提议——失败响应仍是最后一条消息，重试依然有意义——且只附加在发给 webview 的副本上，不会在内存历史里累积。

## 设计说明

- 重发的做法与 SDK 自动重试在两次尝试之间做的两步一致：丢掉失败响应（只丢 agent state，会话文件照 SDK 自己的做法保留），再以空消息批走会话自己的 prompt 路径继续。不新增任何消息，对话读起来就像连接从未断过。

- 提议的时机是一切自动流程落定之后（`agent_settled`），而非「retry failed」通知出现时：一条规则同时盖住一轮对话死掉的三种方式，一次失败只长一个按钮，且永远在 transcript 末尾。

- 还能不能重发由宿主按会话状态判定，而非由按钮判定（通知会留在 transcript 里，点击天然可能过期）。只有停在 `stopReason === "error"` 上的一轮才成立：重发一轮正常结束的对话会把用户正在读的答案悄悄丢掉。子会话不给这个按钮——一路子代理挂了是汇报给主代理的事，由它决定接下来怎么办。

- 重发依赖的 SDK 入口是私有的，因此做了特性探测；未来 SDK 若改名，该动作退化为「没有按钮」，而不是「按钮失灵」。

## 内部

- 新增 `agent/resume.ts` 模块（可重发判定 + 重发机制），经 `offerRetry()` / `withRetryOffer()` / `retry` webview 消息接入 `ChatBridge`；webview 在新的可操作通知卡片上绘制该动作，卡片不进默认折叠的 work block，按钮才可达。
- `diagnostics.ts` 新增两个离线自检项：`manual retry` 钉住 SDK 私有 prompt 路径的存在、以及重发不凭空制造用户消息；`replayed retry offer` 从一个停在失败响应上的会话文件出发，经 `PiRuntime` 与真实的 `ChatBridge.attach()`，一直钉到实际 post 出的 `history` 消息。
